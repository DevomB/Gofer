# ADR 0008: MCTS value sign and terminal scoring

## Status

Accepted Sep 2026. Engine-level fix; affects every result produced before it, including the recorded 9x9 baseline and all self-play data generated by v3 and by early v4 runs.

## Context

While validating the v4 gate ([ADR 0007](0007-pipeline-orchestrator.md)) we could not make an arena discriminate between two networks. Every net-vs-net game was won by White in 12–32 moves, at every playout count we tried, so the gate score was mechanically 0.500 once colours alternated. Three pieces of evidence pointed at the search rather than the networks:

- `TestArenaIdenticalNetsNoSystematicRoleBias` plays 200 games with **heuristic** evaluators on both sides and logged `stone_black=9 stone_white=179` — no network involved.
- The project's own reference baseline, `.tectonix/reports/arena-9x9-baseline.json` (`make reproduce-9x9-baseline`: Black 600 playouts vs White 200, identical heuristics), recorded **7 Black wins in 200 games**, a 200–0 shutout by role. The side with three times the search lost essentially every game.
- A direct experiment: 20 games at the same settings gave Black 0/20 with games of 11–13 moves.

Two defects explain this.

1. **Inverted value sign in selection.** `puctScore` used `q := c.Mean()`. Node means are stored from each node's own side to move, because `backupLocked` negates the value at every level, and evaluators return the value from the side to move (`Heuristic.Evaluate` negates for White). A child's mean is therefore the *opponent's* view, and selecting the maximum of it picks the move that is best for the opponent. More playouts made the engine reliably weaker.
2. **The search never saw the end of the game.** `isTerminal` returned true only when no legal non-pass move existed; two consecutive passes — the rule every game loop actually uses — were not terminal, and `leafValue` asked the evaluator even for a finished position. The search could not see that passing into a pass ends the game, so with komi it walked into lost endings.

The second defect alone did not produce the symptom: fixing it changed nothing measurable. The first was decisive.

## Decision

- `puctScore` scores children from the parent's side: `q := -c.Mean()`. First-play urgency stays a pessimistic constant in the same frame.
- `gameOver` treats two consecutive passes as the end of play, and `terminalValue` scores such a position exactly with `Ruleset.Score` from the side to move.
- Terminal results are never served from or stored in the transposition table: the Zobrist key covers stones, not pass history, so a finished position and a live one can share a key.
- The expensive "no legal move" test runs once per node at expansion; the hot path keeps only the O(1) two-pass test.

## Consequences

- Measured on the baseline command (Black 600 playouts vs White 200, identical heuristics, 20 games, seed 42): Black went from **0/20 to 13/20**, and games from 11–13 moves to 20–69. Search now converts into strength, which is the premise the whole training loop rests on.
- **Every strength number recorded before this fix is void**, including `.tectonix/reports/arena-9x9-baseline.json` and any win rate in older changelog entries or reports. The baseline must be regenerated.
- Fair komi for equal heuristic engines at 50 playouts moved from "about 0 to −1" (a constant fitted to the broken engine) to roughly **+2.5**. Tests that encoded the old value were updated.
- All self-play data produced before the fix carries policy targets from a search that preferred the opponent's best move. It is not worth training on; no long run had been done, so nothing of value was lost.
- CI could not have caught this: `.github/workflows/ci.yml` runs `go test ./... -short`, and every arena-scale test is skipped in short mode. A fast strength-sanity test that runs in short mode was added: with identical evaluators, the side with more playouts must win a clear majority.
