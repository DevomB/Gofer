\subsection{What the pipeline found: five defects in the engine}
\label{sec:pipeline-found}

The first thing the v4 gate did was refuse to work. Running it on real networks,
every net-versus-net game was won by White in 12--32 moves, at every playout
count we tried. Because the arena alternates colours, the candidate's score was
then mechanically $0.500$ and no gate could ever decide anything. Chasing that
led to five defects, all older than v4 and all invisible to the test suite. We
give them in the order the evidence forced us to find them, because the order is
the point: each fix removed one explanation and left the symptom in place.

\paragraph{1. The search preferred the opponent's best move.}
Node values are stored from each node's own side to move: the backup negates the
value at every level, and evaluators return the value from the side to move. A
child's mean is therefore the \emph{opponent's} view, and selection must negate
it. It did not, so the search maximised the opponent's value and more search made
the engine weaker.

\paragraph{2. The search could not see the end of the game.}
Two consecutive passes end a game in every game loop, but the search did not
treat them as terminal, and scored finished positions with the evaluator instead
of the rules. Passing into a pass therefore looked ordinary, and with komi the
engine walked into lost endings. We added the two-pass rule and exact terminal
scoring, and kept terminal results out of the transposition table, whose key
covers stones but not pass history.

\paragraph{3. The arena favoured one role.}
With both engine fixes in, a 200-game match between two evaluators that are
\emph{literally the same code} still split 126--74 by role. Per-game seeds were
linear in the game index (\code{seed}\,$+2i$, \code{seed}\,$+2i+1$, and
\code{seed}\,$+(i{+}1)k$ for the opening sampler), while the colour swap
alternates on the same parity $i \bmod 2$. Neighbouring seeds draw correlated
openings, so one parity class---which is exactly one role---was systematically
decided. Measured with identical evaluators over 120 games, one parity class won
100\% of its games as White, and \emph{which} class flipped with the seed:

This mattered more than the numbers suggest: the gate attributes wins by role, so
a biased role split is a biased promotion decision. Self-play used the same
consecutive seeds and now uses the same mixing.

\paragraph{4. On $9\times9$, the search never left the root.}
The three fixes above did not lengthen the games, so the symptom was still
unexplained. The arena's node storage is a slice, and its accessor returns a
pointer into it. Expanding a node took that pointer, appended the children---which
reallocates the slice once they outgrow its capacity---and then wrote the
``expanded'' flag through the pointer, into the array that had just been
discarded. The initial capacity is 64 nodes and a $9\times9$ root has 82
children, so on every $9\times9$ search the root stayed unexpanded: each playout
broke out of the descent immediately, the transposition table answered all the
later ones with the root's own value, and \textbf{no child was ever visited}.
Move selection takes the most-visited child, all of them zero, so the engine
played the first legal move no matter how long it searched. Every test in the
suite uses a board small enough that the reallocation never happens.

\paragraph{5. All the search went down one line.}
With the root finally expanded, 200 playouts put 100\% of their visits on a
single move. First-play urgency was a flat $-0.2$ in the child's frame, far below
a typical node value, so the first child to be visited could never be outscored.
The visit distribution \emph{is} the policy training target, so this would have
trained every network on one-hot targets. Urgency is now the node's own value
minus a reduction that grows with the explored prior, as in
\citet{wu2019accelerating}.

The same experiment before and after, with identical settings---40 games, one
seed, identical heuristic evaluators on both sides, a symmetric configuration,
and Black searching 600 playouts against White's 200:

Search now converts into strength, which is the premise the entire loop rests on.
Two further checks: with identical evaluators at fair komi, 200 games split
99--101 by colour, and a 200-playout search spreads its visits over many moves
instead of one. Black wins $60\%$ while also conceding komi 6.5, which at these
playout counts favours White (\cref{sec:pipeline-found-komi}).

\paragraph{Fair komi moved with the fix.}
\label{sec:pipeline-found-komi}
Two tests in the repository encoded a ``fair komi'' of $-1$ for equal heuristic
engines, with a comment explaining that tournament komi was not fair at test
playout counts. That constant had been fitted to a search that stopped at the
root: games ended near-empty and komi alone decided them. Measured again on the
repaired engine, at 50 playouts over 100--150 games per point, Black scores
$58\%$ at komi 0, $51\%$ at $0.5$, $46\%$ at $1.0$, $42\%$ at $1.5$, $34\%$ at
$3.5$ and $29\%$ at $6.5$. Fair komi for these engines is near $0.5$, where 200
games split 99--101, and the tests now use that. The value moved twice during
this work, once per round of engine fixes, which is a reminder that such a
constant is a measurement of the engine, not a property of the game.

\paragraph{Why nothing caught it.}
Two things hid these defects. The repository's continuous integration runs
\code{go test ./... -short}, and every arena-scale test skips itself in short
mode; and the unit tests all use boards small enough that the node array never
reallocates, so the defect that mattered most could not appear in them. One test
did observe a symptom---it logged 9 Black wins in 188 games with identical
evaluators---but it asserted only on role balance and explained the colour skew
away in a comment.

Three tests now run in short mode and fail on the old code: root children must
be visited at all, the visits must spread over more than a handful of moves, and
selection, given two root children with equal priors and visits, must prefer the
one whose subtree is worse for the opponent. All three are unit tests, instant
and deterministic. We first wrote a game-playing version instead---three times
the search must win a majority---and it did fail on the broken engine, reporting
4 wins in 11 decisive games; but at these playout counts the outcome is noisy
enough that we would not trust it as a gate in continuous integration.

\paragraph{And six in the orchestrator.}
\label{sec:pipeline-eval-review}
An adversarial review of the orchestrator, run as a separate exercise against the
resume and publish paths, found six defects of its own. Four concerned failure
handling: an interrupt left the trainer and the arena running, because the
process wrapper never signalled the child and the code meant to stop background
self-play was unreachable; a job killed mid-write left a truncated arena report,
which the gate then cached forever and crashed on at every resume; a prefetched
shard could enter the previous cycle's training window, because the learner reads
its shard directory newest-first, so overlap silently changed what a cycle
trained on depending on wall-clock timing; and replaying an interrupted publish
after a failed regression check promoted the failed generation back over its
replacement. Two concerned publishing: the regression baseline picked the most
recently appended matching generation rather than the highest-numbered one, which
after a rollback is an older network than intended, and the seed gate's result
against the heuristic---the only evidence about generation~1---was dropped from
the lineage because it was not a scalar. All six are fixed and covered by tests.
None would have been caught by a passing test suite; they needed someone to ask
what happens when the machine is killed at each point in the cycle.

\paragraph{Consequences for this report.}
Every strength number produced before these fixes is void, including the
committed baseline and the gate scores in \cref{sec:pipeline-eval}, which were
measured while the search was still stopping at the root. No long training run
had been done, so no trained model was lost; the self-play data generated so far
carries policy targets from a search that never descended, and is not worth
training on.

\subsection{Pipeline end to end}
\label{sec:pipeline-eval}

\paragraph{Tests.}
The Go side has 20 tests across three files. Seven cover the shard writer: the NPY
header layout, a round trip of real self-play output through the ZIP container
checking \cref{eq:score-identity} on every row, next-ply policy labelling, and
rejection of rows that would mix board sizes, carry non-finite floats or omit
ownership. Seven cover the search defects of \cref{sec:pipeline-found}. Six cover
atomic artifact writes, including the Windows rename retry.

The orchestrator has 37 tests. They replace Go, PyTorch and ONNX Runtime with a fake
executor that writes the same output files the real tools would. They cover:
\begin{itemize}
  \item a three-cycle run with a seeded first champion, an SPRT acceptance that stops before
        the cap, and an SPRT rejection;
  \item a failure injected into training, followed by a resume that neither repeats
        self-play nor counts rows twice;
  \item reuse of cached gate batches after a restart;
  \item skipping training below the row threshold; hold mode; background self-play;
        in-process and sidecar command lines; pruning of old outputs;
  \item the window formula; shard archiving; configuration parsing and validation; the
        Elo and SPRT arithmetic, including the exact gate model of \cref{sec:orch-gate}
        cross-checked against an independent Monte Carlo simulation;
  \item the defects of \cref{sec:pipeline-eval-review}: an interrupt must not orphan a
        background job, a prefetched shard must not enter the current cycle's window, a
        truncated arena report must be replayed, and a replayed publish must not restore a
        demoted generation;
  \item publishing: every champion kept in the registry, the alias and latest release
        moving forward, a failed regression match holding back or demoting a champion,
        failed uploads retried, and rollback that renumbers nothing.
\end{itemize}

\paragraph{End-to-end runs.}
We ran the real loop with the smoke configuration on the machine described in
\cref{sec:eval} (an Intel Core i7-1185G7 with 16\,GB of memory). It used the real Go
engine, learner, exporter and arena, with tiny settings: 8 games per cycle, 24/8 playouts
with $p=0.25$, one or two training epochs, and gates of 20 games at 16 playouts.
\Cref{tab:pipeline-e2e} lists stage times for a three-cycle run on the repaired engine.
An earlier pair of runs, one per inference backend, is what the backend comparison below
reports; their gate results are void (\cref{sec:pipeline-found}), but the timings and the
backend ratio are not affected by the search defects.

\paragraph{Observations.}
\begin{itemize}
  \item \emph{Overlap.} Both later cycles waited at most 0.04\,s for self-play, because
        their games had been produced in the background while the previous cycle trained,
        exported and gated. In an earlier run one cycle waited 20.9\,s: overlap hides
        self-play only up to the length of the other stages.
  \item \emph{Backend.} The same 20-game gate took 1.6\,s in-process and 8.9\,s over
        sidecars. The sidecar figure includes starting two inference servers and waiting
        for them to report healthy, which dominates at this scale.
  \item \emph{Reproducibility.} The same seeds gave identical row counts under both
        backends (659 and 663), including the cycles where self-play used the network.
        This is consistent with the per-game seeding of \cref{sec:selfplay-search}, but it
        is not proof of bit-identical games.
  \item \emph{Gate behaviour.} The smoke networks are deliberately worthless---one or two
        epochs on a few hundred positions---and the gate says so. The seeded champion lost
        all 10 games to the heuristic evaluator, and each later candidate scored exactly
        10--10 against it: with two equally weak networks and alternating colours, every
        game goes to whoever holds White, so the score is 0.500 by construction. The
        likelihood ratio stayed at $-0.10$, the cap was reached and the fallback rejected.
        Before the search fixes this table looked the same, which is what made the defects
        so hard to see; the difference is that the games now vary in length (6--24 moves
        against the champion, up to 83 against the heuristic) instead of being 10 copies
        of one game.
  \item \emph{Data.} Shards took 12--38\,KB per cycle. They were loaded by the learner
        without conversion, and the parity-checked export succeeded in every cycle.
\end{itemize}
A full smoke run takes about three minutes of wall-clock time for three cycles, including
the engine build.

\paragraph{Gate length and error rates.}
\Cref{tab:orch-gate-oc} in \cref{sec:orch-gate} gives the exact operating characteristics
of the v3 and v4 gates. It is derived analytically, from the implemented decision code,
not measured from games. Its central results are a false-promotion rate of $2.7\%$ for v4
against $8.0\%$ for v3 at zero true gain, and longer v4 gates near zero gain.

\paragraph{Not yet measured.}
We have not run the container build, any GitHub workflow, a GPU run, or a free-runner
training run. No network trained by v4 has been compared with a v3 champion. These gaps
are listed with the other limitations in \cref{sec:limitations}.
