\subsection{What the pipeline found}
\label{sec:pipeline-found}

The first thing the v4 gate did was refuse to work. Running it on real networks,
every net-versus-net game was won by White in 12--32 moves, at every playout
count we tried. Because the arena alternates colours, the candidate's score was
then mechanically $0.500$ and no gate could ever decide anything.

Chasing that produced eight defects, all older than v4 and all invisible to the
test suite (\cref{tab:found-defects}); a later reading of the engine added two
more (\cref{sec:pipeline-eval-codereview}). They fall into two groups. Five are in the
search: they made the engine play badly and, worse, made the data it generated
worthless. Three are in the measurement apparatus, and these are not a separate
category of bug so much as the reason the other five were survivable: each one
supplied a plausible explanation that made the next one invisible. We give them
in the order the evidence forced them out, because that order is the finding.
After each of the first three fixes the symptom was still there.

\paragraph{1. The search preferred the opponent's best move.}
Node values are stored from each node's own side to move: the backup negates the
value at every level, and evaluators return the value from the side to move. A
child's mean is therefore the \emph{opponent's} view, and selection must negate
it. It did not, so the search maximised the opponent's value and more search made
the engine weaker.

\paragraph{2. The search could not see the end of the game.}
Two consecutive passes end a game in every game loop, but the search did not
treat them as terminal, and scored finished positions with the evaluator instead
of the rules. Passing into a pass therefore looked ordinary, and with komi the
engine walked into lost endings. We added the two-pass rule and exact terminal
scoring, and kept terminal results out of the transposition table, whose key
covers stones but not pass history.

\paragraph{3. The arena favoured one role.}
With both engine fixes in, a 200-game match between two evaluators that are
\emph{literally the same code} still split 126--74 by role. Per-game seeds were
linear in the game index (\code{seed}\,$+2i$, \code{seed}\,$+2i+1$, and
\code{seed}\,$+(i{+}1)k$ for the opening sampler), while the colour swap
alternates on the same parity $i \bmod 2$. Neighbouring seeds draw correlated
openings, so one parity class---which is exactly one role---was systematically
decided. Measured with identical evaluators over 120 games, one parity class won
100\% of its games as White, and \emph{which} class flipped with the seed:

This mattered more than the numbers suggest: the gate attributes wins by role, so
a biased role split is a biased promotion decision. Self-play used the same
consecutive seeds and now uses the same mixing.

\paragraph{4. On $9\times9$, the search never left the root.}
The three fixes above did not lengthen the games, so the symptom was still
unexplained. The arena's node storage was one slice, and its accessor returned a
pointer into it. Expanding a node took that pointer, appended the children---which
reallocates the slice once they outgrow its capacity---and then wrote the
``expanded'' flag through the pointer, into the array that had just been
discarded. The initial capacity was 64 nodes and a $9\times9$ root has 82
children, so on every $9\times9$ search the root stayed unexpanded: each playout
broke out of the descent immediately, the transposition table answered all the
later ones with the root's own value, and \textbf{no child was ever visited}.
Move selection takes the most-visited child, all of them zero, so the engine
played the first legal move no matter how long it searched. Every test in the
suite uses a board small enough that the reallocation never happens.

Raising the initial capacity would only move the threshold at which the mistake
reappears, so the storage is now fixed-size chunks that are allocated once and
never resized: a pointer stays valid for the life of the arena, and the class of
error is gone rather than postponed. Search time is unchanged.

\paragraph{5. All the search went down one line.}
With the root finally expanded, 200 playouts put 100\% of their visits on a
single move. First-play urgency was a flat $-0.2$ in the child's frame, far below
a typical node value, so the first child to be visited could never be outscored.
The visit distribution \emph{is} the policy training target, so this would have
trained every network on one-hot targets. Urgency is now the node's own value
minus a reduction that grows with the explored prior, as in
\citet{wu2019accelerating}.

\paragraph{6. Forced playouts flooded the root.}
\Citet[\S3.2]{wu2019accelerating} forces extra playouts on ``each child of the
root that has received any playouts'', so a move the search never looked at gets
none. \gofer{} forced a floor of $k$ on \emph{every} child, and did it before the
main search rather than after. On $9\times9$ that is 82 children, so at a
200-playout budget the forced pass outnumbered the search itself. It flattened
the visit distribution, and it made the policy-target pruning a no-op, because
every child had been forced above the two-visit threshold that pruning uses.
Restricting forcing to visited children, after the search, sharpens the targets
measurably: over 154 full-search positions at 200 playouts, the top move went
from $0.159$ to $0.199$ of the visits, the number of moves with any visits from
$41.5$ to $24.3$, and the entropy from $2.98$ to $2.60$ nats, against $4.41$ for
a uniform distribution over 82 moves.

The same fix also returns the compute the flood was consuming. Because the
forced pass cost roughly (children $\times$ $k$) playouts per move---about 164 on
$9\times9$---regardless of the search budget, the saving is largest where the
budget is smallest. Measured on self-play with every move at the full cap, one
seed, cost per move:

\begin{tabular}{@{}rrrr@{}}
\toprule

\midrule
6   & 53.3\,ms & 16.1\,ms & $3.3\times$ \\

200 & 171.4\,ms & 95.3\,ms & $1.8\times$ \\

\noindent At 200 playouts that matches what the arithmetic predicts, since 164 of
364 playouts were forced. At 6 playouts the arithmetic predicts far more than the
measured $3.3\times$, because per-move costs that do not scale with the budget---
building features, generating legal moves, cloning the board---dominate there,
and because the repaired search descends deeper, so each remaining playout does
more work. This is a saving on work that should never have been done, not a
faster implementation of the same work.

\paragraph{7. The reference baseline enhanced both players.}
Forced-playout mode (\code{-arena-enhanced}) was resolved by comparing evaluator
\emph{names}: the enhanced side was whichever engine's name matched the baseline's.
The project's reproducible baseline command passes the same evaluator name on
both sides, so both engines were enhanced and \code{baseline} silently meant
\code{both}. Because forced playouts act at the root, which is where defects 3
and 4 lived, this masked them in precisely the measurement meant to detect a
strength change: re-running that command after repairing the search moved its win
counts not at all. The mode now follows the baseline \emph{role} across the colour
swap. The difference is not subtle, at 600 versus 200 playouts over 60 games:

\toprule

\code{baseline} & 62\% & 41 moves \\
\code{both}     & 70\% & 21 moves \\
\bottomrule
\end{tabular}
\end{center}

\noindent The baseline command now uses \code{none}, so it measures search scaling
rather than forced-playout behaviour.

\paragraph{8. Measurement runs stopped on the statistic they measured.}
A match ends as soon as its promotion gate is decided. The accept branch is
guarded by a minimum game count, which tests raise to disable it, but the reject
branch is not, so a 200-game bias measurement silently played 169 games---stopping
exactly when the challenger fell behind. That is optional stopping correlated
with the quantity under test, the same error class this report attributes to the
v3 gate (\cref{sec:orch-gate}), here inside the harness rather than the gate. The
same rule ran inside every batch of the v4 gate, putting a second stopping rule
on the stream the SPRT was already testing sequentially. Batches now play out in
full. Re-deriving the gate's operating characteristics without the inner stop
moves them very little---false promotions at zero true gain from $2.4\%$ to
$2.3\%$---which is worth stating plainly: it was a correctness problem, not a
large bias.

\paragraph{What the fixes are worth.}
The same experiment before and after, with identical settings---40 games, one
seed, identical heuristic evaluators on both sides, a symmetric configuration,
and Black searching 600 playouts against White's 200---gives 0/40 before and
24/40 after, with the median game growing from 28 moves to 80.

The project's own reproducible baseline (\code{make reproduce-9x9-baseline}: 200
games, the same matchup) makes a sharper record, because it was run at four
points in this work and its answer moved each time:

Three things in that table are worth stating rather than leaving to the reader.

First, the answer to ``is three times the search worth anything'' moved from
$-576$ to $+131$ Elo. That is not an error of magnitude but of sign: the
committed reference baseline asserted that tripling the search was
catastrophically harmful, and that file sat in the repository as the project's
strength record.

Second, rows two and three are identical---133/67, the same Elo, means of 20.0
and 19.6 moves, the same maximum of 33---although every individual game record
differs between them. That is the measurement demonstrating that it was not
measuring what had just been repaired: \code{-arena-enhanced} was silently
enhancing both sides (defect~7), and forced root playouts were deciding the
moves either way.

Third, the cleanest signal of the regime change is not the win rate but the game
lengths: \emph{the longest game in either middle run, 33 moves, is shorter than
the median game of the final run, 76}. The final run's distribution is 8 games
under 20 moves, 39 from 20 to 49, 62 from 50 to 79 and 91 at 80 or more, against
an original mean of 12.9. Those are not two samples from a shifted distribution;
they are two different processes. Throughout, Black concedes komi 6.5, which at
these playout counts favours White (\cref{sec:pipeline-found-komi}), so the
figure is measured against a handicap and understates the search advantage.

Fourth, the last row is a warning about reading any of the others too closely.
It is the same command after the transposition table was repaired
(\cref{sec:pipeline-eval-codereview}), and its win rate is lower than the row
above. That difference is not resolvable: a second seed on the repaired engine
returns 142 of 200, the two pool to 278 of 400, and the before-and-after
comparison, by a two-proportion $z$-test with the
pooled variance under the null, gives $z = 1.27$, $p = 0.20$. Pooled, the deeper search is worth $+143$ Elo
with a 95\% interval of $[+106, +180]$. Put more directly: $+186$ carries the
interval $[+131, +241]$ and $+131$ carries $[+80, +182]$, which overlap over
almost their whole length, so there was never a 55-Elo drop to account for. A
single 200-game arena gives a 95\% interval roughly \emph{105} Elo wide;
doubling to 400 narrows it to 74. These numbers separate $-576$ from $+131$
reliably and separate nothing within the repaired engine at all. The two
repaired runs do agree on the median game length, 55 moves each.

There is a methodological trap here worth naming, because we fell into it. The
$+186$ had been quoted as settled on the strength of a reproducibility
argument: the configuration hash matched, the command was deterministic, the
tree had not moved underneath the measurement. All of that was true and none of
it bears on precision. Establishing that a number is reproducible is a claim
about provenance; establishing that it is precise is a claim about sample size,
and the first can be mistaken for the second exactly because it feels rigorous
and is usually the harder discipline to maintain. The rule we would take from
it: no Elo figure leaves this project without its interval, and no
single-sample number goes onto a public surface at all.

Two further checks: with identical evaluators at fair komi, 200 games split
99--101 by colour, and a 200-playout search spreads its visits over many moves
instead of one.

\paragraph{Fair komi moved with the fix.}
\label{sec:pipeline-found-komi}
Two tests in the repository encoded a ``fair komi'' of $-1$ for equal heuristic
engines, with a comment explaining that tournament komi was not fair at test
playout counts. That constant had been fitted to a search that stopped at the
root: games ended near-empty and komi alone decided them. Measured again on the
repaired engine, at 50 playouts over 100--150 games per point, Black scores
$58\%$ at komi 0, $51\%$ at $0.5$, $46\%$ at $1.0$, $42\%$ at $1.5$, $34\%$ at
$3.5$ and $29\%$ at $6.5$. Fair komi for these engines is near $0.5$, where 200
games split 99--101, and the tests now use that. The value moved twice during
this work, once per round of engine fixes, which is a reminder that such a
constant is a measurement of the engine, not a property of the game.

\paragraph{Why nothing caught it.}
Two things hid these defects. The repository's continuous integration runs
\code{go test ./... -short}, and every arena-scale test skips itself in short
mode; and the unit tests all use boards small enough that the node array never
reallocates, so the defect that mattered most could not appear in them. One test
did observe a symptom---it logged 9 Black wins in 188 games with identical
evaluators---but it asserted only on role balance and explained the colour skew
away in a comment.

Three tests now run in short mode and fail on the old code: root children must
be visited at all, the visits must spread over more than a handful of moves, and
selection, given two root children with equal priors and visits, must prefer the
one whose subtree is worse for the opponent. All three are unit tests, instant
and deterministic. We first wrote a game-playing version instead---three times
the search must win a majority---and it did fail on the broken engine, reporting
4 wins in 11 decisive games; but at these playout counts the outcome is noisy
enough that we would not trust it as a gate in continuous integration.

\paragraph{Why they were survivable.}
None of these defects crashed. Every one produced a number that a reasonable
person could explain. A search that returns the first legal move looks like a
weak engine on a small budget. A flattened visit distribution looks like a
network that has not learned yet. A zero-filled ownership row looks like a
neutral board. A match that stops at 169 of 200 games looks like a clean sample,
because nothing reports the number it was asked for. The most expensive instance
is not in the code at all: a note in the repository's known-issues file recorded
the White-heavy colour split as expected from komi and first-move advantage,
which is a true statement about Go and a false explanation of that measurement.
It closed the investigation for two months.

The general lesson we take from this is about which experiments are worth
running early. The measurement that eventually broke the case open---more search
must beat less search, with everything else held equal---is not a test of any
feature. It is a test of whether the system's most basic premise holds, and its
expected answer was known in advance, so a wrong answer could not be rationalised
away. A project with no compute budget can afford several such experiments; what
it cannot afford is a training run whose result it has no way to interpret.

\paragraph{And six in the orchestrator.}
\label{sec:pipeline-eval-review}
An adversarial review of the orchestrator, run as a separate exercise against the
resume and publish paths, found six defects of its own. Four concerned failure
handling: an interrupt left the trainer and the arena running, because the
process wrapper never signalled the child and the code meant to stop background
self-play was unreachable; a job killed mid-write left a truncated arena report,
which the gate then cached forever and crashed on at every resume; a prefetched
shard could enter the previous cycle's training window, because the learner reads
its shard directory newest-first, so overlap silently changed what a cycle
trained on depending on wall-clock timing; and replaying an interrupted publish
after a failed regression check promoted the failed generation back over its
replacement. Two concerned publishing: the regression baseline picked the most
recently appended matching generation rather than the highest-numbered one, which
after a rollback is an older network than intended, and the seed gate's result
against the heuristic---the only evidence about generation~1---was dropped from
the lineage because it was not a scalar. All six are fixed and covered by tests.
None would have been caught by a passing test suite; they needed someone to ask
what happens when the machine is killed at each point in the cycle.

\paragraph{And two more, found by reading rather than measuring.}
\label{sec:pipeline-eval-codereview}
A later pass over the whole engine, made for code quality rather than
correctness, turned up two defects of exactly the shape described above. Both
had been present throughout the work of this section.

The first is the clearest instance in this report of an instrument returning a
plausible number. Constructing an ONNX evaluator went through four functions,
two of them mutually recursive, one of which decided which model it was building
by comparing the URL it had been handed against the configured second sidecar.
On the sidecar path the resolved model was discarded and the primary URL
substituted, which made that comparison unreachable. The consequence is that
\code{-eval-backend sidecar} with a champion in one slot and a challenger in the
other pointed both engines at the same sidecar. Every sidecar-backed gate was
the champion playing itself, and returned a win rate near $0.500$---which is
precisely the value a correctly functioning symmetric match is supposed to
produce. A wrong result that coincides with the expected result is not
detectable by inspecting the result.

The second is in the transposition table. Slots were indexed by the Zobrist hash
modulo the table size, but no key was stored in the slot, so any two positions
agreeing in the low 16 bits returned each other's evaluation. With $2^{16}$
slots a collision becomes likely after a few hundred distinct positions, and a
single $9 \times 9$ search visits far more than that, so wrong values were being
backed up the tree throughout. The symptom is a search that plays slightly worse
than its evaluator should permit, which is indistinguishable from a weak
evaluator. The record field that should have held the key instead held a
\code{Depth} that was written as the constant $1$ at all three store sites and
never read as anything but non-zero.

The methodological point is that these two were not found the way the previous
eight were. The eight came out of experiments with predictable answers; these
came out of reading the code with no hypothesis, asking only whether each piece
said what it meant. The two methods find different things. An experiment cannot
see a defect whose output matches the expected output, and reading cannot tell
you which of the plausible behaviours the system actually exhibits. A project
that can afford neither a large test suite nor much compute gets more from
alternating them than from either alone.

\paragraph{Consequences for this report.}
Every strength number produced before these fixes is void, including the
committed baseline and the gate scores in \cref{sec:pipeline-eval}, which were
measured while the search was still stopping at the root. No long training run
had been done, so no trained model was lost; the self-play data generated so far
carries policy targets from a search that never descended, and is not worth
training on.

That accounting was incomplete, and the way it was incomplete is worth stating,
because we only noticed weeks later. Marking data void is the obvious half of
the job. The other half is asking what was decided on the strength of it, and
that question does not ask itself: void data sits in a directory where someone
will trip over it, whereas a conclusion drawn from void data has already been
written up, accepted, and filed somewhere that reads as settled. In our case a
net-size ablation had compared four architectures by validation loss on a frozen
snapshot of exactly this self-play output. Policy is the dominant term in that
loss, so every figure in it measured how well each network fit a target
containing no search. The conclusion survived only by luck: the ablation had
recommended changing nothing, so nothing was built on it. Had it recommended a
smaller trunk, we would have adopted an architecture on the strength of a
measurement of noise and had no reason to revisit it.

The practice we would adopt from this is a mechanical one. Whenever a dataset is
declared void, enumerate the decisions taken on it and mark each one explicitly,
even where the decision happens to stand. A decision whose evidence has
evaporated is not automatically wrong; it is unsupported, and the distinction is
invisible unless someone writes it down.

\subsection{Pipeline end to end}
\label{sec:pipeline-eval}

\paragraph{Tests.}
The Go side has 20 tests across three files. Seven cover the shard writer: the NPY
header layout, a round trip of real self-play output through the ZIP container
checking \cref{eq:score-identity} on every row, next-ply policy labelling, and
rejection of rows that would mix board sizes, carry non-finite floats or omit
ownership. Seven cover the search defects of \cref{sec:pipeline-found}. Six cover
atomic artifact writes, including the Windows rename retry.

The orchestrator has 37 tests. They replace Go, PyTorch and ONNX Runtime with a fake
executor that writes the same output files the real tools would. They cover:
\begin{itemize}
  \item a three-cycle run with a seeded first champion, an SPRT acceptance that stops before
        the cap, and an SPRT rejection;
  \item a failure injected into training, followed by a resume that neither repeats
        self-play nor counts rows twice;
  \item reuse of cached gate batches after a restart;
  \item skipping training below the row threshold; hold mode; background self-play;
        in-process and sidecar command lines; pruning of old outputs;
  \item the window formula; shard archiving; configuration parsing and validation; the
        Elo and SPRT arithmetic, including the exact gate model of \cref{sec:orch-gate}
        cross-checked against an independent Monte Carlo simulation;
  \item the defects of \cref{sec:pipeline-eval-review}: an interrupt must not orphan a
        background job, a prefetched shard must not enter the current cycle's window, a
        truncated arena report must be replayed, and a replayed publish must not restore a
        demoted generation;
  \item publishing: every champion kept in the registry, the alias and latest release
        moving forward, a failed regression match holding back or demoting a champion,
        failed uploads retried, and rollback that renumbers nothing.
\end{itemize}

\paragraph{Observations.}
\begin{itemize}
  \item \emph{Overlap.} Both later cycles waited at most 0.04\,s for self-play, because
        their games had been produced in the background while the previous cycle trained,
        exported and gated. In an earlier run one cycle waited 20.9\,s: overlap hides
        self-play only up to the length of the other stages.
  \item \emph{Backend.} The same 20-game gate took 1.6\,s in-process and 8.9\,s over
        sidecars. The sidecar figure includes starting two inference servers and waiting
        for them to report healthy, which dominates at this scale.
  \item \emph{Reproducibility.} The same seeds gave identical row counts under both
        backends (659 and 663), including the cycles where self-play used the network.
        This is consistent with the per-game seeding of \cref{sec:selfplay-search}, but it
        is not proof of bit-identical games.
  \item \emph{Gate behaviour.} The smoke networks are deliberately worthless---one or two
        epochs on a few hundred positions---and the gate says so. The seeded champion lost
        all 10 games to the heuristic evaluator, and each later candidate scored exactly
        10--10 against it: with two equally weak networks and alternating colours, every
        game goes to whoever holds White, so the score is 0.500 by construction. The
        likelihood ratio stayed at $-0.10$, the cap was reached and the fallback rejected.
        Before the search fixes this table looked the same, which is what made the defects
        so hard to see; the difference is that the games now vary in length (6--24 moves
        against the champion, up to 83 against the heuristic) instead of being 10 copies
        of one game.
  \item \emph{Data.} Shards took 12--38\,KB per cycle. They were loaded by the learner
        without conversion, and the parity-checked export succeeded in every cycle.
\end{itemize}
A full smoke run takes about three minutes of wall-clock time for three cycles, including
the engine build.

\paragraph{Gate length and error rates.}

not measured from games. Its central results are a false-promotion rate of $2.7\%$ for v4
against $8.0\%$ for v3 at zero true gain, and longer v4 gates near zero gain.
